# 引擎分发 P1：demucs-onnx 与原版 demucs 输出质量对比

> 验证日期：2026-07-26 ｜ 结论：**质量达标，可进入 P2**，但 macOS 侧路线需重新权衡（详见下文）

## 一、验证方法

- **引擎**：原版 demucs 4.0.1（PyTorch 2.8.0）vs demucs-onnx 0.3.4（onnxruntime 1.28.0 + numpy）
- **模型**：htdemucs（四轨），双方均 fp32；均在 **CPU** 上运行以排除后端数值差异
- **素材**（3 组，覆盖全部 4 个 stem 的有效内容）：
  1. `车上片段.mp3` — 45 秒真实人声录音（验证 vocals）
  2. demucs 官方 `test.mp3` — 20 秒真实音乐，鼓/其他声部为主（验证 drums、other）
  3. `fullband.wav` — test.mp3 混入合成 65Hz 低音线（验证 bass；纯正弦对模型是较苛刻输入）
- **指标**：逐 stem 计算 SI-SDR（以 PyTorch 输出为参考）、皮尔逊相关系数、最大绝对差、差值 RMS。参考 RMS < 1e-3 的近静音 stem 判为 N/A（SI-SDR 在近静音信号上无意义——这是首轮误判为"差异显著"的原因）
- 对比脚本：`compare.py`（ffmpeg 解码 f32 + numpy，见会话 scratchpad `p1-compare/`）

## 二、结果：有效 stem 全部高度一致

| stem | 素材 | SI-SDR (dB) | 相关系数 | 结论 |
|---|---|---|---|---|
| vocals | 真实人声 | **26.95** | 0.99906 | 听感不可区分 |
| drums | 真实音乐 | **23.65** | 0.99785 | 听感不可区分 |
| drums | 混合素材 | 22.30 | 0.99707 | 听感不可区分 |
| other | 真实音乐 | **28.18** | 0.99924 | 听感不可区分 |
| other | 混合素材 | 26.40 | 0.99886 | 听感不可区分 |
| bass | 合成低音 | **15.64** | 0.98662 | 轻微差异（苛刻输入下仍可接受）|

近静音 stem（如人声录音里的鼓轨）两引擎都输出近静音，绝对差 RMS ≤ 0.001，不影响结论。

**质量结论：ONNX 路线不牺牲分离质量。** 建议 P2 前用一首完整歌曲人耳 A/B 抽检一次（本轮输出留存于 scratchpad `p1-compare/torch-out*/`、`onnx-out*/`）。

## 三、性能与体积实测（Apple Silicon 本机）

| 维度 | 原版 demucs | demucs-onnx | 备注 |
|---|---|---|---|
| 45s 音频耗时（CPU）| 19.4s | 28.9s | ONNX 慢 ~1.5× |
| 20s 音频耗时（CPU）| 10.6s | 19.2s | ONNX 慢 ~1.8× |
| 45s 音频耗时（MPS）| **~8–10s** | ❌ 不可用 | 见 CoreML 失败 |
| venv 体积 | 429M（mac 版 torch 无 CUDA）| **154M** | HANDOFF 中 "~2GB" 仅适用于 CUDA 版 |
| htdemucs 模型 | **80M**（.th）| 315M fp32 / 166M fp16 | ONNX 模型反而更大 |
| 环境+模型合计 | ~510M | ~470M (fp32) / ~320M (fp16) | mac 上体积优势不明显 |

### ⚠ 关键发现：CoreML 执行器编译失败

demucs-onnx 默认 `--providers auto` 在 macOS 上选择 CoreML，但 htdemucs.onnx 编译报错：

```
onnxruntime ... Fail: Error compiling model: compiler error: Espresso exception:
"Invalid argument": generic_general_slice: Invalid values 2048 in begin_ids for input_shape 1
```

必须显式 `--providers cpu` 才能运行。**即 macOS 上 ONNX 路线目前没有 GPU 加速**，比现有 torch+MPS 路径慢 2–3 倍。

## 四、对 P2 的建议

按平台拆分路线，而不是单一 ONNX 路线：

- **Windows**：维持 ONNX 计划（onnxruntime DirectML 有 GPU 加速、torch Windows 无 DML；PyInstaller 冻结 demucs-onnx CLI + fp16 模型 166M）。DML 可用性需在 Windows 实机验证（P2 首项）。
- **macOS**：两个选项待 P2 决断：
  1. PyInstaller 冻结**原版 demucs**（含 mac 版 torch，~430M，保留 MPS 加速，模型仅 80M）——速度最优；
  2. 继续 ONNX + CPU（~154M + 166M fp16）——体积略优但慢 2–3 倍；关注上游 CoreML 修复（github.com/StemSplit/demucs-onnx issue 跟踪）。
- 两条路线都沿用现有引擎发现逻辑（`resources/engine/`），对应用层无侵入。

## 五、复现命令

```bash
# 原版（CPU）
demucs -n htdemucs --float32 --clip-mode rescale -d cpu -o out/ input.mp3
# ONNX（CPU，CoreML 会编译失败）
demucs-onnx separate --model htdemucs --providers cpu --precision fp32 input.mp3 out/
# 对比
python compare.py out/htdemucs/input out-onnx/
```

环境：python3.12 venv + `pip install demucs-onnx`（需 Python ≥3.11）。
