# 引擎分发 P2：冻结打包与应用接入

> 完成日期：2026-07-26 ｜ macOS 已实测通过；Windows 构建链已就绪，DML 待实机验证

## 一、macOS：原版 demucs 冻结路线（已实测 ✅）

**决断**：按 P1 结论选择冻结原版 demucs（PyInstaller），而非 ONNX：

| | 原版冻结（选定）| demucs-onnx 冻结 |
|---|---|---|
| 引擎体积 | 511M | 118M |
| 模型体积 | 80M（四轨）+53M（六轨）| 315M fp32 / 166M fp16 |
| 加速 | **MPS ✅** | 仅 CPU（CoreML 编译失败）|
| 速度（45s 音频）| **~13–17s（含启动）** | ~29s（纯 CPU 推理）|
| 质量 | 基准本身 | ≈基准（P1 已验证）|

两个实验的冻结产物都验证过可运行；ONNX 路线若上游修复 CoreML 可重新评估（体积可省 ~300M）。

**实测结果**（打包版 `Stem Studio.app`，无任何环境变量）：
- 引擎自动发现 `Contents/Resources/engine/bin/demucs` ✅（进程表确认）
- MPS 正常，45 秒音频全流程 17 秒（冻结 torch 启动开销约 +4s，可接受）
- 应用总体积 818M（Electron ~265M + 引擎 511M + 应用）
- 进度条 NN% 与现有 `nextProgress` 解析器兼容，无需改应用代码

**关键坑（已解决）**：冻结入口必须先 `multiprocessing.freeze_support()`，
否则 demucs 的 DataLoader 子进程会带 `-B -S -I -c` 参数重新执行冻结二进制
并报 "unrecognized arguments"。见 `scripts/build-engine-mac.sh`。

## 二、Windows：demucs-onnx + DirectML 路线（构建链就绪，待实机）

Windows 无 MPS，torch 也无 DML 支持，onnxruntime-directml 是 GPU 加速唯一现实选项。

- **适配层** `engine/demucs_shim.py`：以原版 demucs CLI 契约（参数子集、
  `NN%` 进度行、`<root>/<模型>/<曲目>/<stem>.<扩展名>` 布局）驱动
  demucs_onnx API，应用零改动换引擎。已在 macOS 用 venv 冒烟验证 ✅
  （进度换算、输出布局、`-d` 映射、错误行兼容 `classifyFailure`）。
  视频输入由 shim 先用 ffmpeg 抽音轨（soundfile 读不了视频容器）。
- **构建脚本** `scripts/build-engine-win.ps1`：venv → `demucs-onnx[mp3]` +
  `onnxruntime-directml` → PyInstaller 冻结 shim 为 `demucs.exe` →
  整理为 `engine-dist/Scripts/` 布局。
- **CI** `.github/workflows/build-engine.yml`（workflow_dispatch 手动触发）：
  双平台冻结引擎并上传 artifact。
- ⚠ 待 Windows 实机验证：DML 执行器在 htdemucs 上是否可用（CoreML 在 mac
  编译失败的先例说明不能想当然）；不可用时 shim 会自动落到 CPU。

## 三、打包流程变化

- `package.json` 新增 `extraResources: engine-dist → resources/engine`
- 打包前需先构建引擎（`engine-dist/` 与 `.venv-engine/` 已 gitignore）：
  - macOS：`bash scripts/build-engine-mac.sh`（一键安装脚本已自动串联）
  - Windows：`powershell -File scripts/build-engine-win.ps1`
- 模型不随包分发：原版引擎首次分离自动下载到 `~/.cache/torch`（四轨 80M、
  六轨 53M）。应用内下载进度提示已有（`nextProgress.downloading`）。
  带校验与断点续传的应用内模型管理归 P3。
